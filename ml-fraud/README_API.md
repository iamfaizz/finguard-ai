# FinGuard AI — ML Fraud Detection API

## 1. Overview

The ML Fraud service provides transaction fraud scoring using the
V2 XGBoost model and SHAP-based explanations.

- Service: `ml-fraud`
- Port: `8001`
- Framework: FastAPI
- Model: XGBoost V2
- Explainability: SHAP TreeExplainer
- Input: 17 precomputed transaction features

**Important:** This service does not accept raw transactions or
generate transaction-history features. The caller must generate
the 17 features before calling `/score`.

## 2. Docker Setup

Build the image from the `ml-fraud` directory:

```bash
docker build -t finguard-ml-fraud:local .
```

Run the container:

```bash
docker run -d \
  --name finguard-ml-fraud \
  -p 8001:8001 \
  finguard-ml-fraud:local
```

Check container status:

```bash
docker ps
```

For Docker Compose integration, the backend should call:

```text
http://ml-fraud:8001
```

This assumes the Compose service is named `ml-fraud` and both
containers share a Docker network.

## 3. Health Endpoint

### GET /health

Checks whether the fraud service and model have loaded.

Example response — HTTP 200:

```json
{
  "status": "ok",
  "service": "ml-fraud",
  "model_version": "fraud_v2"
}
```

## 4. Fraud Scoring Endpoint

### POST /score

Accepts exactly 17 precomputed features for one transaction.

Content-Type:

```text
application/json
```

### Request fields

| Field | Type | Validation |
|---|---|---|
| n_prior | integer | >= 0 |
| is_debit | integer | 0 or 1 |
| hour | integer | 0–23 |
| is_night | integer | 0 or 1 |
| day_of_week | integer | 0–6 |
| amount | number | > 0, finite |
| amount_z_user | number | finite |
| amount_ratio_cat | number | finite |
| amt_to_prev_balance | number | finite |
| is_new_merchant | integer | 0 or 1 |
| is_new_device | integer | 0 or 1 |
| is_new_city | integer | 0 or 1 |
| hour_bucket_share | number | finite |
| txn_10m | integer | >= 0 |
| txn_1h | integer | >= 0 |
| txn_24h | integer | >= 0 |
| secs_since_last | number | >= 0, finite |

Extra fields are rejected. Missing fields and invalid values
return HTTP 422.

### Example request

```json
{
  "n_prior": 17,
  "is_debit": 1,
  "hour": 13,
  "is_night": 0,
  "day_of_week": 2,
  "amount": 1065.4,
  "amount_z_user": -0.7873017913,
  "amount_ratio_cat": 0.5982620415,
  "amt_to_prev_balance": 0.2157881412,
  "is_new_merchant": 1,
  "is_new_device": 0,
  "is_new_city": 0,
  "hour_bucket_share": 0.3529411765,
  "txn_10m": 2,
  "txn_1h": 2,
  "txn_24h": 2,
  "secs_since_last": 88.0
}
```

### Example response — HTTP 200

```json
{
  "fraud_probability": 0.8165499568,
  "risk_level": "HIGH",
  "reasons": [
    "Only 88 seconds since your previous transaction",
    "2 other transactions in the last 10 minutes",
    "This is the first time you have paid this merchant"
  ],
  "model_version": "fraud_v2"
}
```

The example represents the previously tested transaction
TXN00018074. Actual scores and explanations depend on the input.

## 5. Risk Classification

The API returns one of three risk levels:

| Risk level | Condition |
|---|---|
| HIGH | Score >= threshold loaded from V2 metadata |
| MEDIUM | Score >= 0.45 and below HIGH threshold |
| LOW | Score below 0.45 |

The HIGH threshold is loaded from `fraud_v2_meta.json`.
The MEDIUM threshold is currently hard-coded as `0.45`.

The returned fraud probability is the model's raw
`predict_proba` output. It should not be interpreted as a
calibrated probability of fraud.

## 6. SHAP Explanations

The service uses SHAP TreeExplainer to identify the strongest
feature contributions for each prediction.

- Returns up to three explanation reasons.
- Reasons are generated by the existing `top_reasons` logic.
- If no explanation passes the current rules, a fallback
  message is returned.
- The fallback does not mean the transaction is risk-free.

## 7. Error Responses

| HTTP status | Meaning |
|---|---|
| 200 | Successful response |
| 422 | Missing, invalid or unexpected input fields |
| 500 | Fraud scoring failed |

The service loads the model and metadata during application
startup. Missing model artifacts prevent startup.

## 8. Integration Contract

The expected request flow is:

1. Backend retrieves the user's transaction history.
2. Backend uses the V2-compatible feature builder.
3. Feature builder produces the 17 required features.
4. Backend sends the features to `POST /score`.
5. Fraud service returns the score, risk level, reasons
   and model version.
6. Backend handles persistence and frontend response.

The feature builder must preserve the V2 training-time
feature calculations to avoid training-serving inconsistencies.
